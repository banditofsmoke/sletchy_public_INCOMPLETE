# Adversarial coverage - attack → test

The map of what Sletchy actually resists, and what it does not. Required by
[LAW 10](../../docs/LAW/laws.md#law-10).

**Two sections, and the second one matters more.** Anything not listed under Coverage is
not covered, regardless of how confident the design doc sounds. New security work adds a
row to one section or the other - "probably fine" is not a coverage claim.

---

| **Job Object + restricted token + AppContainer combined** | isolation | Each verified alone or assumed. The combination is what `winjob` actually ships, and one may void another. Untested until #13. |
| **Isolation findings are build-specific** | isolation | ADR-0005 measured 10.0.19045 only. A different Windows build may behave differently; the probe records the build it ran on. |
| **Side channels** | isolation | Timing, cache, and resource-contention channels between sandboxed processes on a shared host. Out of scope; stated so it is not implied-covered. |
| **Malicious model files** | forge / mind | `.pkl` / `.pt` deserialisation is executable content in disguise. Currently only treated as untrusted input under L4; needs its own gate. |
| **Host processes outside the bubble** | scope | Sletchy secures what it launches, not the whole machine. A consequence of [ADR-0001](../../docs/adr/0001-no-kernel-driver.md), and it must not be oversold. |
| **Physical / offline attack on `var/`** | storage | Ledger tampering is *detected*, not *prevented*, by an attacker with disk access. Detection is the design goal. |
| **Prompt injection generally** | mind | Capabilities are Kernel-issued and not self-grantable, which bounds the blast radius. It does not stop an agent being talked into misusing what it already legitimately holds. |
| **The self-check runs as the user it reports on** | cli | Anything that controls the user's account can fake every check. The window says so on the same screen as the score (`DOES_NOT_PROVE`). That is disclosure, not a fix. |
| **The files check trusts a build number, not a measurement** | cli | It passes on build 19045 because ADR-0005 measured that build. It does not re-measure containment at runtime, so a changed Windows component under the same build number would still pass. |
| **`sletchy bridge` run by hand has no Job Object** | bridge | The job is applied by the desktop shell that starts it (ADR-0008). Run from a terminal, the bridge is the operator's own process, exactly like the CLI. |
| **The window trusts WebView2** | desktop | A strict CSP allows nothing remote, but a flaw in the WebView2 runtime itself is outside anything the shell controls. It is Microsoft's, ships with Windows, and updates with it. |
| **The job's process limit is close to the Kernel's real depth** | LAW 0 §5 | The Kernel is four processes on Windows (uv launcher, its conhost, venv redirector, interpreter), and each panic helper brings its own conhost: 6 of the job's 8 while panic runs. Measured on 10.0.19045: a lone `cmd /c exit` counts as 2 in a job. A helper that ran two at once would be refused by the job, and that refusal is not yet tested. |
| **The shell's tests need Node and Rust** | desktop | They run in CI (`desktop (windows)`) and on a developer machine with both; `uv run pytest` covers only the structural half (`test_desktop_shell.py`). |
| **No test clicks inside the real window** | desktop | Vitest drives the screens against the preview; the e2e test drives the real Kernel over real pipes without the WebView; the Rust tests start the real Kernel inside its job. The whole chain - a click in WebView2, through Rust, into the Kernel - was exercised by hand on 2026-10-02, not by a test. `tauri-driver` with WebdriverIO would close it. |
| **Adding a program to the allowlist is not recorded** (#52) | supervisor | `var/allowlist.toml` is read at each `sandbox run`. Each launch records the name it was allowed under, but editing the file, which widens what may run, leaves no entry of its own. Whoever can write `var/` can allowlist a program. |
| **`sandbox run` has no streaming output and no stdin** (#52) | cli | Output arrives when the program ends, because the capture is read at the end, and the program gets no input. Fine for short commands, wrong for long or interactive ones. |
| **A pin is only as good as the commit it froze** (#34) | LAW 4 | Each action and hook is pinned to the commit its release named on the day it was pinned. A release that was already bad is frozen bad. Whether a pinned action runs on a runtime GitHub is retiring is not checked offline: GitHub's own warning on each run is the signal, and it is how the move to Node 24 was found (2026-10-04). Updating a pin is a reviewed change, never automatic. |
| **No vulnerability check or quarantine run yet** (#34) | LAW 4 | The vetting record says why each package is here and what it is for. What a dependency does when it runs, and its known vulnerabilities, are still #34's to build. Vetting decisions are not ledger entries yet. |
| **The Rust crates' licences are not checked** (#34) | LAW 4 | `Cargo.lock` carries checksums, not licences, and reading them needs `cargo metadata`, which this check does not run. |
| **An allowlisted program that is itself dangerous is allowed** (#69) | supervisor | The allowlist is only as good as its author. An allowed interpreter given a hostile script, or an allowed program given hostile arguments, runs: the supervisor checks the program, not the arguments. |
| **A program replaced on disk after it was allowlisted** (#69) | supervisor | The allowlist holds a resolved path, not a hash, so a different file at the same path runs. Pinning a hash would close most of it, and is not built. |
| **The tripwire list is incomplete, and matches names** (#69) | supervisor | A signed Windows program not on the list, or a listed one copied under another name, is not caught by it. The allowlist is the control: neither runs unless someone allowlists it. |
| **Backends can still be called directly from Python** (#69) | supervisor | Every launch should go through the supervisor, and the first command-line route (#52) does. Nothing yet stops other Python code constructing a backend itself. |
| **A single write can pass a root's ceiling by its own size** (#68) | fsguard | The quota is checked before a write, against the size the caller declares. A caller that writes more than it declared, or two writers at once, can overshoot. Counting walks the root on every check. |
| **A network drive mapped to a letter looks local to fsguard** (#68) | fsguard | `Z:\x` passes the share rule because it is spelled like a local path. A root on such a drive is the operator's choice; fsguard does not ask Windows what kind of drive a letter is. |
| **`var/` as a whole has no single 5 GB ceiling yet** | LAW 0 §5 | LAW 0's table gives `var/` 5 GB, checked by fsguard. fsguard now has per-root ceilings (#68), and the ledger (1 GB) and the payloads (3 GB) have their own, but nothing yet declares `var/` as a root with the 5 GB total. |
| **A secret in a shape the list does not know is shown as it is** (#86) | secrets | `ledger show --payload` and `ledger.payload` mask the shapes in `kernel/secrets/shapes.py`, the same list the commit-time scanner uses. A password, a token from a provider not on the list, or a key split across two lines is printed. Shape matching is a backstop, not a guarantee. |
| **Two processes writing payloads at once can pass the 3 GB ceiling** | LAW 0 §5 | Each process counts the store once, on its first write, and adds what it writes itself, so it does not see what another process wrote since. The overshoot is at most what the other wrote. The 2 GB free-space floor is read from the drive on every write, so the disk is never filled either way. Today only the Warden's recorder writes payloads, from one process. |
| **A copy of a system program inside the Windows folder passes** (#146) | SOC | The rule checks the folder, not who signed the file. A publisher check is not built yet, and a signature says who made a program, not whether it is safe. |
| **Unelevated, most processes cannot be opened** (#146) | SOC | 145 of 210 on 2026-10-04: services and Windows' own core processes. They are counted and shown as "could not read". The service list would name most of them, and reading it needs a decision on the LAW 0 catalogue, which refuses every `SC_MANAGER_` right, read-only ones included. |
| **A process or connection between two looks is never seen** (#146) | SOC | The sensor runs on demand. Watching continuously needs a long-running Sletchy (#59) and a CPU ceiling. |
| **An exposed service on a port the list does not know is not flagged** (#146) | SOC | `EXPOSED_SERVICES` names 15 database and remote-control ports. Every listener is still shown, with whether it is reachable from the network. |
| **Command lines of running processes are not read yet** (#146) | SOC | They would be masked with the secret shapes before display or recording. Startup commands are read, and masked. |
| **Startup places the sensor does not read** (#146) | SOC | It reads the startup keys, the Startup folders, automatic services and boot or logon tasks. Not: the logon shell and init values, DLLs loaded into every program, debugger redirections, WMI subscriptions, browser extensions, or services started on demand. Each is a way a program can stay on a machine. |
| **A signature says who, not whether it is safe** (#146) | SOC | A signed program in a user folder is not named. Windows files signed through a catalogue rather than in the file read as unsigned to this check; they live in the Windows folder, which the user-folder rule never asks about. |
| **The event sensor reads four entries of one log** (#146) | SOC | Service crashes (7031, 7034) and unexpected shutdowns (41, 6008) in the System log. Program hangs and crashes (the Application log), disk errors and driver warnings are not read. A loop under 24 failures a day is not called one. |

## Rules for this file

- A row moves from **Planned** to **Coverage** only when the test exists and passes.
- A row moves to **Residual gaps** the moment someone identifies an attack we do not
  handle - *before* it is fixed, not after.
- Deleting a residual-gap row requires the test that closes it, in the same PR.
- Tests never target the host's real services or any third party. Only Sletchy's own
  sandboxed surfaces, with inert fixtures. ([LAW 0 §6](../../docs/LAW/00-do-no-harm.md))
